# グローバル作業ルール

以下の方針をすべての作業に適用する。対象リポジトリや、より深い階層に
`AGENTS.md` がある場合は、そのプロジェクト固有のルールも併せて適用する。

## 目的と進め方

- 依頼の目的、制約、期待する成果物、指定された作業順序を最初に整理する。
- ユーザーが「まず調査する」「実装前に議論する」「内容をレビューしてから変更する」
  などの順序を指定した場合、その段階を飛ばして先へ進まない。
- 対象リポジトリの既存コード、設定、データ、ドキュメント、運用方法を確認してから
  提案や実装を行う。既存方式を再利用できる場合はそれを優先する。
- 参照先として示されたリポジトリやファイルは、明示的な依頼がない限り変更しない。
  変更対象と参照対象を区別する。
- 期限と目的を満たす最も単純な案から検討する。将来の拡張だけを理由に、現時点で
  不要なサービス、パイプライン、抽象化、設定、評価項目を追加しない。
- 依頼された作業は、許可された範囲で検証と後処理まで完了させる。未実装、未検証、
  レビュー待ち、外部確認待ちを完了扱いにしない。

## 調査と判断

- ユーザーが明示した事実と、コード・設定・実データから確認できた事実を優先する。
- 確認済みの事実、推測、提案、仮定、未確認事項を区別する。確認していない仕様、
  分類、名称、データフロー、指標定義を作らない。
- 最初に思いついた案だけで結論を出さない。代替案の調査を求められた場合は、
  実在する選択肢、公式情報、既存実装、現在の制約を確認して比較する。
- 分析結果や集計値が直感や定義と矛盾する場合、説明を付けてそのまま進めない。
  イベント定義、対象期間、タイムゾーン、粒度、結合、重複、分母、データソースを
  再確認する。
- 業務データの名称や区分は、実データと既存の業務用語を優先する。独自の言い換えや
  存在しないカテゴリを追加しない。

## 説明と成果物

- 結論と全体像から詳細へ進む順序で説明する。
- 設計判断の理由、対応する制約、失うものは、その設計の直後に記載する。離れた
  セクションを往復しないと意図が分からない構成にしない。
- 表は、複数案の比較、マッピング、同じ項目を持つ一覧に有効な場合だけ使う。
  設計意図や因果関係を表のセルへ分断しない。
- セクション数、網羅性、文書量を目的にしない。対象の規模とリスクに応じて必要な
  内容だけを書く。
- 日本語では、誰が、何に対して、何をしたのかが分かる名称と説明を使う。主語や
  対象を省略して曖昧な指標名・説明にしない。
- 一次情報や基準を表す際は、「現行仕様の根拠」「管理元」「基準となる設定」など、
  文脈に即した具体的な表現を使う。

## 変更とレビュー

- ユーザーが変更前のレビューを求めた作業では、変更対象、現状、提案内容、差分、
  実行する操作を提示し、承認されるまで変更しない。この確認条件は同じ作業中、
  ユーザーが解除するまで維持する。
- 外部システムを更新する場合、対象とpayloadを事前に確認し、更新後は保存された
  状態を再取得して検証する。必要と指定された場合は変更前のバックアップも保存する。
- Hunkにユーザーコメントがある場合は全件を読み、各コメントについて、修正したか、
  調査の結果変更しなかったか、追加確認が必要かを明示する。修正後は差分を
  再読み込みし、未対応コメントがないことを確認する。
- ユーザーがセルフレビューを求めた場合は、差分、テスト、仕様との整合性、不要な
  変更、未完了事項を確認し、見つけた問題は可能な範囲で修正してから報告する。

## 実装

- skillの作成・変更には`create-validated-skill`を使用し、毎回、安価な構造検証と
  関係するscript検査を行う。意味を変えない修正は確認範囲と行動試験の省略理由を
  記録する。文言だけの変更でも指示の意味が変わるなら行動変更として扱う。
- 行動変更は変更要件と重要な既存要件を覆うfresh agentの限定的なsmokeから始める。
  比較は新規なら候補版とskillなし、改訂なら候補版と既存版を基本とし、三条件は
  主張に必要な場合だけ行う。新規能力、大改訂、高リスク操作、モデル・ツール変更、
  smokeの不一致では検証を広げる。採用前には、変更を導いていない課題で凍結版を
  確認する。未使用のsmoke課題がこの確認を兼ねてよく、毎回三つの評価セットを
  作る必要はない。発火条件はその変更・既知の問題に応じて確認する。
- ユーザーの必須意図・禁止事項を優先し、必須要件の失敗時は採用しない。許可された
  独立チェックの結果は個別に記録し、省略・時間切れ・予算切れを成功扱いしない。
  実行環境が使えない場合はblocked、証拠不足は判定保留とする。静的検査や少数の
  smokeを一般的な性能向上の証明とせず、意図への忠実さと品質・追加コストを分ける。
- 現在の実行形態に合わせてモジュールの名称と責務を決める。CLI、バッチ、サービス
  など過去の形態に由来する不適切な命名や分割を残さない。
- 既存の設定注入、Secret管理、環境変数、共通設定、パイプライン実行方式を確認し、
  同じ値や仕組みを重複して定義しない。
- Pythonリポジトリがuvを利用している場合、依存関係、実行コマンド、補助ツールを
  uvで管理し、別のパッケージ管理方法を追加しない。
- 期待する挙動をテストまたは実行結果で検証しながら実装する。実装内容に応じて
  対象テストを実行し、必要なら全体の品質チェックも行う。
- PRを前提とする変更では、既定ブランチから作業用ブランチを作成し、既定ブランチへ
  直接コミットしない。リポジトリ固有のブランチ・PR規則があればそれを優先する。
- ユーザーの既存変更や今回の対象外の差分を、勝手に修正、削除、整形、コミットしない。

## tkによる記録

- tkで管理されている作業では、開始時に対象タスクと既存の進捗・recordを確認する。
- 意味のある進捗、失敗、設計判断、発見、ブロッカー、ブロッカー解消、次のアクション
  が生じた時点で記録する。
- 作業終了時に、progress logだけでなく、decision、finding、blocker、question、
  hypothesisの追加や、既存recordのsupersede、resolve、obsolete、verifyが必要かを
  監査する。
- レビュー待ちは`in_review`、未着手は`todo`、実行中は`in_progress`として扱い、
  実際に成果が完了した場合だけ`done`にする。
