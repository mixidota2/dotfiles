# ヒアリング準備と実施後反映のワークフロー（hearing-workflow）

関係者（業務部門・システム開発担当・上長など）へのヒアリング準備と、実施後の記録・設計更新・`tk` 反映を手戻りなく進める。日本語の記述は `explain-before-shorten` に従い、主語（どの部署の誰が）を明確にして書く。

## 1. ヒアリング・相談の準備フェーズ（「聞く動機」の先行合意）

「〜さんに何をどう聞くか整理したい」「相談の準備メモを作って」と言われたときは、いきなり細かい機能仕様や連携I/Oの質問リストをファイルに書き出さない。相手から見て**「なぜ自分たちにそれを聞きに来たのか」の動機と全体像が伝わるストーリーライン**を先にチャットで短く提示し、合意してから文書化する。

### ステップ1: 4段のシンプルなストーリーラインを先に提示する
既存の `memo/` と `tk` の決定事項を確認したうえで、まず次の4点だけを箇条書きで提示して方向性をすり合わせる。

1. **自分たちの全体ミッションとアプローチ**: 局所的な機能作成ではなく、本来解きたい業務課題と全体構想は何か（例：内製化を機に、事前検討から事後検証・知見蓄積まで回るサイクルを作りたい等）。
2. **相手の担当領域・システムとの接点**: 相手が担っている業務やシステム（例：iMAP、ストマネ、現場の棚割運用）が、全体構想のどこに関わるか。
3. **今回話を聞きたい動機**: 特定の出力連携や機能実装を「至上命題」のように押し付けず、真の動機を率直に言語化する。
   - 業務上の使われ方の認知ギャップをなくしたい（自分の想定している最終出力先や前提が実態とズレていないか確かめたい）
   - 相手側の直近の開発予定と機能が重複して無駄になるのを避けたい（ただし相手側の開発待ちでこちらの検討を止める前提にはしない）
   - データ取得や連携の現実的な口（API・ファイル入出力の有無）を知り、どこまでをスコープにするか判断したい
4. **当日確認したい具体的な質問（3〜5点）**: 上記の動機から自然に導かれる質問項目。

### ステップ2: 合意後に準備メモを保存する
ストーリーラインの合意が取れたら、`memo/<project>/hearings/YYYY-MM-DD_<相手>_ヒアリング準備.md` に整理して保存する。

## 2. ヒアリング・実演終了後の反映フェーズ（`kiku` からの一気通貫反映）

「ヒアリング終わったのでまとめて」「実演のフィードバックを記録して `tk` に入れて」と言われたときは、以下の4ステップを漏れなく実行する。

### ステップ1: 一次記録（`~/.kiku/meetings/`）の確認
- `~/.kiku/meetings/` 配下から該当日の会議ディレクトリを探し、`minutes.md` や発言録（トランスクリプト）を読む。文字起こしに固有名詞の誤変換がある場合は、既存の `memo/` の用語（iMAP、ストマネ、たなナビ、荒利益、DPT、ゴンドラ等）と照合して正しく補う。

### ステップ2: ヒアリング記録の作成・追記
- 既存の `*_ヒアリング準備.md` がある場合はそこに「記録」節を追記し、新規に記録ファイルを作る場合（`memo/<project>/hearings/YYYY-MM-DD_<相手>.md`）は不要な「準備」節を作らず「記録」から書き始める。
- 記録には、(1) 全体の評価・合意した方向性、(2) 新たに判明した業務フロー・システム分担の事実、(3) もらった改善点・要望（誰のどの操作に関する指摘か）、(4) 残った確認事項を分けて記載する。

### ステップ3: 企画・設計ドキュメント（`README.md` 等）の更新
- ヒアリングによって Open Questions が解消したり、スコープ・入出力方針（例：「外部システムへの自動書き込み連携は求めず、プラン検討までにとどめる」等）が決まったりした場合は、該当する `README.md` や設計書の該当節を更新する（依頼があれば確認の上で反映する）。

### ステップ4: `tk` へのログ・決定事項・子タスクの反映
- 親タスクに対して `tk log <parent_id> --summary "..." --details "..."` を記録し、重要な設計決定や判明事実は `tk record add <parent_id> --kind <decision|finding> --log-id <log_id> --summary "..."` で昇格させる。
- プロトタイプ改修などのフィードバック対応タスクを作る場合は、`tk add "<タイトル>" --parent <parent_id> --description "..."` で作成し、`description` を以下の4節に分けて書く：
  - **目的**（誰に何を見せられる・使える状態にするか）
  - **前提**（ヒアリング記録ファイルのパスと発言録パス、合意した前提）
  - **完了条件**（「必須で対応する項目」と「検討にとどめる項目」を番号付きで明確に分ける）
  - **Non Goal**（今回扱わない範囲）
