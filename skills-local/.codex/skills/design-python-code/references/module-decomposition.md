# Module分割と統合

## Flat packageを維持する条件

次の状態なら、package直下に複数の`.py`が並んでいても問題にしない。

- package全体が一つの凝集した能力を表す。
- file名から責務と主要なcallerを推測できる。
- public APIが安定し、内部file配置がconsumerへ露出していない。
- 代表変更が少数の関連fileへ局所化する。
- 状態、不変条件、権限のownerが衝突していない。
- directoryを追加しても依存や理解が明確にならない。

file数だけで閾値を決めない。

## 分割を検討する兆候

- `services.py`、`models.py`、`utils.py`が複数の無関係な用語・変更理由を持つ。
- 同じprefixのfile群が固有の状態やadapterを共有する。
- 一機能の変更でpackage全体の多数fileを編集する。
- import cycle、条件分岐、共有mutable stateが増えている。
- public consumerが内部fileを直接importしている。
- 一部だけをtest、replace、deleteすることが難しい。

## ファイル分割の粒度（細切れファイルの禁止）

1つの動詞・1つの関数・1つの操作ごとにファイルを細切れにする分割（`apply.py`、`recommend.py`、`operations.py`、`run.py`など）は行わない。

- 最初は1パッケージにつき1〜3個の凝集したファイルから始める。
- 同じ状態・同じ不変条件・同じ概念を扱う操作群は1つのモジュールにまとめる。
- ファイルを分割するのは、モジュールが肥大化し、かつ独立して理解・テストできる明確な下位責務（例：純粋なルール検証と外部形式からのパーサなど）に分かれる場合だけにする。

## 『リーダブルコード』に基づく命名原則

名前を見ただけで「何のデータか」「何を入力して何を計算するか」「状態変更や外部I/Oを伴うか」が誤解なく伝わる名前を選ぶ。

1. **汎用的で空虚な名前を禁止する**
   - `utils.py`、`common.py`、`helpers.py`、`misc.py`を新しい責務の逃げ場にしない。
   - `manager`、`service`、`processor`、`handler`、`data`、`info`、`item`のような中身を説明しない広い語を避け、具体的な役割名にする。
   - `apply.py`、`process.py`、`execute.py`、`do_*.py`のように動詞1つだけのファイル名を付けない。
2. **標準的な技術用語や多義語との衝突を避ける**
   - `model.py`：データモデルなのか機械学習モデルなのか、何の業務概念なのか判別できないため単体ファイル名として使わない（共有データ型は`models/<概念名>.py`のように具体的な概念名にする）。
   - `table.py`：RDBのテーブル定義に見えるため、集計表やルックアップ構造のモジュール名に使わない。
   - `count_*.py`、`plan.py`、`record.py`など、複数の意味（「件数を数える」と「本数」、「計画」と「案」、「記録する動詞」と「履歴データ」など）に読める語は、誤読されない具体的な名詞・複合語にする。
3. **層の役割と名前の形を一致させる**
   - `models/`配下：ドメイン概念の名詞（データの形と不変条件のみを持ち、外部I/Oや手続きを持たない）。
   - 専門モジュール：専門領域と計算対象が分かる名詞、関数名は入力・出力・計算内容が明確な動詞＋目的語。
   - `use_cases/`：業務上のユースケース（一連の手続き）を表す名前。
   - `infra/`：接続先の技術が分かる名前（`bigquery.py`、`*_client.py`、`*_store.py`等）を推奨する。業務の操作や対象ごとの名前（「確定発注の書き出し」等）でファイルを分けない。
