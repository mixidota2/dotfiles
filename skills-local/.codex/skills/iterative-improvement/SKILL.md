# 反復改善ループのプロトコル（iterative-improvement）

離席中やまとまった時間バジェットで「複数観点のサブエージェントレビュー → 改修 → 検証」を複数ラウンド自律的に回すときは、1ラウンドだけで勝手に終了したり、逆に頼まれていない過剰機能を際限なく盛り込んだりしないよう、以下の収束ループを守る。

## 1. ラウンドの基本構造（Review → Triage → Implement → Verify）

各ラウンドは次の5ステップを順番に完結させる。

1. **先入観なしの複数観点・独立レビュー**:
   - 直近コミット差分（`git log` / `git diff`）と対象コード・UIに対して、独立したレビュアー（Pi では `code-reviewer` サブエージェントの `gemini-4-carbon` 等、Claude Code ではサブエージェント＋`pi -p --model google-vertex/gemini-4-argon`）を観点別（例：①操作UX・視点維持、②データ整合・エッジケース、③5層境界・保守性、④画面文言・日本語の明快さ）に並列起動する。
   - 親の懸念を誘導的に渡さず、根拠（`ファイルパス:行番号`）付きの指摘だけを出させる。
2. **トリアージとスコープ膨張防止（引き算の原則）**:
   - 複数レビュアーが共通して指摘した問題、および P0/P1（バグ、状態同期漏れ、ズーム/パンのリセット、スコープ漏れ、分かりにくい日本語ラベル）だけをそのラウンドの採用対象に絞る。
   - **禁止事項**: 頼まれていない新規画面・過剰な設定項目・「決めること：」等のメタバッジを足して複雑度を上げない。
3. **分離 worktree での実装と片付け**:
   - 実装（Pi では `worker` サブエージェント `gemini-4-argon`）は `worktree: true` または作業用ブランチで分離して行い、稼働中のデモ環境（`main`）を途中で壊さない。
   - マージ・統合が完了したら、そのラウンドで作った一時 worktree と一時ブランチ（`git worktree list`）を必ず削除する。
4. **全層の決定論的検証**:
   - Backend 変更時: `uv run pytest`、`ruff check`、`ty check`（またはプロジェクトの型チェッカー）をすべて通す。
   - Frontend 変更時: `vitest` / `npm test`、`tsc` / `biome check`、`npm run build` を通す（Backend のテスト通過だけで完了扱いにしない）。
   - Pi 使用時: 変更したコードファイルに `lens_diagnostics(source="lsp", scope="paths", paths=[...])` を実行し、古いエラーキャッシュを残さない。
   - HTML 図解・スライド変更時: **最後の編集の後に** ヘッドレスブラウザのスクリーンショット等で再描画を確認する。
   - 検証通過後にラウンド単位でコミットする。
5. **収束判定または次ラウンド移行**:
   - 独立レビューで P0/P1（高・中優先度）の指摘が **0件** になれば、時間バジェットが残っていても無理にコードを変えず早期収束する（Pi で反復ループが有効な場合は `autonomy_control({ mode: "converged" })` を呼んで終了する）。
   - P0/P1 指摘を修正した直後のラウンドで、かつ残り時間が十分（終了処理用の残り10分以上）ある場合は、立ち止まらず次のラウンドへ進む。

## 2. ループ終了時の最終チェックリスト

時間バジェットの終盤または収束時に、完了報告を行う前に必ず以下を確認する。

1. `git status -s` と `git worktree list` がクリーンで、不要な一時 worktree が残っていないこと。
2. ローカル開発サーバーを再起動する場合は、停止前に `ps eww -p <PID>` または起動スクリプトで既存の環境変数（`*_ALLOWED_ORIGINS` 等の CORS 設定やポート）を確認してそのまま引き継ぎ、フロントエンド Origin からの `OPTIONS` プリフライトと画面取得（HTTP 200）が通ること。
3. 全ラウンドで実施した変更点・採用しなかった指摘・検証結果を `tk log` に記録すること。
