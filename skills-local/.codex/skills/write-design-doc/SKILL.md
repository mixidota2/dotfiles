# Design Doc を書く

Design Doc は、実装の前に「誰のどの課題を、どの設計とトレードオフで解決するか」を読み手と合意するための文書である。詳細設計書（全関数・全フィールドの仕様）ではない。

## 必須の構成

次の見出しをこの順で必ず置く。見出し名は英語のまま使い、本文は依頼の言語で書く。中身が薄い節も省かず、「該当なし」とその理由を書く。

タイトルの直後は Context and Scope から始める。文書そのものの説明（「この文書は〜を合意するための文書である」等）や、仮定の一覧・表を、節の前に置かない。

1. **Context and Scope**
   - **目的 → 現状の課題 → 今回作るものの範囲**の順で書く。既存の業務や既存ツール（他社推奨アプリ等）で何が足りていないかを先に示し、後から唐突に課題が出てくる構成にしない。
   - ここには業務と利用者の話だけを書く。既存のコード・データ基盤・インフラを調べて分かったこと（制約、既存テーブルで足りるか、試算など）は書かず、Analysis に書く。
2. **Goals and Non-goals**
   - **Goals** は達成したい価値で書く。「**誰が（売場構成企画部の担当者・事業部の担当者など具体的な役割）、何を見て・何を判断/操作でき、どういう状態になり、どんな価値を得るか**」を主語・述語のある文で書く（例：「ML エンジニアが、インフラを意識せずに、新しいモデルの実験と本番への反映を低い認知負荷で迅速に行える」）。
   - Goals に、技術的に守りたいこと（ガバナンスルールの遵守、層構造、拡張しやすいコード構造などの設計原則）、システムの内部動作（「流れが一通り動く」等）、データ制約を書かない。技術的な制約は Analysis に、それを踏まえた設計は The Actual Design に、合否の数値基準は Tests に書く。
   - **Non-goals** は今回の目標と混同されやすい境界だけに絞る。頼まれていない将来の拡張案（エンハンス、例：「新設・廃止の棚種」等）を勝手に創作して入れない。
3. **Analysis**
   - 設計の前提になる現状の事実を書く。既存のコード・データ基盤・インフラ・過去の分析を調べて分かったこと、設計を縛る制約、既存の資産（既存の mart の組み合わせ等）で足りる部分と足りない部分、必要なら規模やコストの試算を書く。
   - 連携先リポジトリ（dbt 等）がある場合は、そのリポジトリの層制約・チェック（`checks/strict_layer_dependencies.sql` 等）と、既存のテーブルで足りるかを確認した結果をここに書く。
   - 確認した事実には、どこで確かめたか（ファイル名、テーブル名、クエリ結果など）を添え、仮定と分ける。設計の判断（どの案を採るか）はここに書かず、The Actual Design に書く。設計に影響しない調査結果は書かない。
4. **The Actual Design**
   - **最初に「解決の方法」を書く**：Context and Scope の課題をどうやって解決するのかを、システムの詳細より先に書く。「誰がどう使う何のシステムか」と、課題を解決する考え方・手法・全体の流れを示す。データ基盤との連携やコードの構成から書き始めない。
   - 「作るもの」「設計の柱」「解決の道筋」のような曖昧な見出しや、「失うもの」という不自然な定型句は使わず、**トレードオフ**（または自然な文で「その代わり〜」）と書く。
   - **機械学習・データ分析の設計書**では、The Actual Design を次の順で書く。
     1. **解決の方法**：課題をどういう問題として捉えるか（予測、最適化、効果検証、分類など）、どの手法で解くか、その手法がこの課題に妥当な理由、手法が成り立つ前提と、前提が崩れたときの限界を書く。効果検証なら、比較対象の選び方、推定の方法、前提の確かめ方、結果の不確かさの示し方まで書く。手法の名前を挙げるだけで済ませない。
     2. **システム**：System-context diagram と Code design。
     3. **データ**：使うデータ、粒度、期間、手法が必要とする加工、データの欠けや偏りへの対応。
     4. **評価**：手法の出来を何の指標で、何と比べ、どのデータの分け方で測り、どの水準なら採用するか。
   - **System-context diagram**：このシステムと、具体的な利用者・外部システム・データの境界と流れを Mermaid の `flowchart`（`ID["ラベル"]` と1対1エッジ）で描き、直後に要点を添える。
   - **Code design**：最初に層の分け方と依存の向きを1〜2文で示し、続けて**ディレクトリ構成を必ずツリー（`├──`）で載せる**。ツリーには作るディレクトリとファイルをすべて書き、各行にその責務を1行のコメントで添える。読み手はこのツリーを見て構成が妥当かを判断するので、文章や箇条書きだけで済ませない。ツリーの後に、分け方の理由とトレードオフを書く。Python なら `design-python-code` スキルを使い、次の**標準5層構造と命名原則**に従って整理して書く：
     1. **共有データモデル（`models/`）とモジュール内部型の分離**：複数モジュール間で受け渡す中核のデータ構造（ドメインエンティティ・値オブジェクト・共有契約）はトップレベルの `models/` に概念（名詞）ごとのファイルで集約し、処理ロジックは書かない。単一モジュール内部でしか使わない設定・中間型や API の Request/Response DTO だけ各モジュール内に閉じる。
     2. **専門モジュール群の独立とトップレベル階層の粒度統一**：各専門モジュール（予測、最適化、ルール検証、効果推定など）は `models/` の型を入出力として自身の専門計算・検証だけを行い、**専門モジュール同士は互いに import しない**（1つの業務モジュールが他の計算モジュールや DB 保存まで抱え込む God モジュール化を禁止する）。トップレベルには同じ粒度のパッケージだけを並べ、1か所からしか使われない下位部品はパッケージ内に収める。一時的な比較・検証処理（他社推奨 Excel の比較等）はアプリ本体に入れず `scripts/` に切り出す。
     3. **インフラ層（`infra/`）とユースケース層（`use_cases/`）によるオーケストレーションの分離**：DB・ファイル・外部API・LLM SDK の入出力は `infra/` に閉じ込める。`infra/` には接続先ごとのモジュール（BigQuery、データベース、オブジェクトストレージなど）だけを置く。「確定発注の書き出し」「予測結果の保存」のような業務の操作や対象ごとにファイルを分けず、業務上の確認や判断（当日分のデータが届いているかの判定など）も持たせない。それらは `use_cases/` が `infra/` のモジュールを呼んで行う。複数の専門モジュールと `infra/` を順番に呼んで1つの業務操作を完結させる手続き的ワークフローは `use_cases/` に置き、入口（`api/`・`cli.py`・AIツール）は `use_cases/` を呼ぶだけにする。コマンドラインから実行するもの（手動のコマンド、定期実行ジョブの起動コマンド）の入口は `cli.py` に統一し、`jobs.py` のような別名のファイルを作らない。
     4. **細切れファイルの禁止と『リーダブルコード』の命名原則**：`apply.py`・`recommend.py`・`operations.py` のように動詞1つ・1操作ごとにファイルを細切れにしない。また、`model.py`（データ型か機械学習モデルか不明）・`table.py`（DBテーブル定義に見える）・`utils.py`・`common.py` のような多義語や標準用語と衝突する曖昧なファイル名を付けない。
     5. **代表的な変更シナリオ（5〜7個）での波及検証**：予測器の追加、最適化手法の追加、画面の変更、予測対象指標の追加、データソースの変更、保存項目の追加、操作ログ取得の追加などに対して「どのモジュールだけを変更すれば済むか」を検証する。
   - 必要に応じて、データ、AIの役割、画面、進め方（M1〜）を小見出しで足す。テストや検証の内容はここに書かず、Tests に書く。
5. **Deployment and Release**
   - 作ったものを、どうやって利用者が使える状態にし、その後どう更新していくかを書く。次の4点を書く。
     - **デプロイの方法**：どの環境に、何を、どの手順や仕組みで配置するか。
     - **ブランチ戦略とリリース戦略（CI/CD）**：コードの変更が利用者に届くまでの流れを、ブランチごとの表で書く。表の列は「ブランチ名」「役割」「PR 作成時の動作」「マージ時の動作」とする。ブランチ名は `main`、`feature/{feature-name}` のように具体的に書く。PR 作成時の動作には自動で行う検査（テスト、lint、型検査など）を、マージ時の動作には何がビルドされ、どの環境へ、自動か手動承認かのどちらで配置されるかを書く。表の後に、問題が起きたときに前の版へ戻す方法を書く。学習処理や定期実行のジョブがある場合は、そのジョブの定義がどう配置・更新されるかも書く。
     - **開発時の検証**：開発者が、開発中の変更を取り込む前にどう確かめるかを書く。手元では確かめられず検証環境への配置が必要なものについて、何を、どの操作で検証環境に配置して確かめるかを書く。配置して確かめる必要があるものだけを書く。
     - **インフラの管理方法**：必要なインフラを何で定義し（Terraform 等）、誰がどう変更するか。
   - 担当者が手元で実行する CLI のように、該当しない項目も省かず、「該当なし」とその理由を1文で書く。検討して不要と判断したのか、抜けたのかを、読み手が区別できるようにする。
6. **Tests**
   - 実装と結果が設計どおりであることを、どう確かめるかを書く。コードのテスト方針（何を単体テストで、何を結合テストで確かめるか）、データの検査、手法や結果の正しさの確かめ方（答えが分かっているデータで期待どおりの結果が出るか等）、受け入れの基準を書く。
   - テストのしやすさやテスト方法の説明を、Code design や Alternatives Considered の中に散らさず、この節にまとめる。
7. **Alternatives Considered**
   - **まず解決の方法の代替案を比べる**。別の手法、別の問題の捉え方、「何もしない」「既存の仕組み（既存 mart の組み合わせ等）をそのまま使う」を、目標と制約に照らして最も単純な案から比べる。データの取り方やコードの構成の代替案だけで終わらせない。
   - 実際に検討した代替案ごとに、良い点、トレードオフ、目標・制約に照らして採らなかった理由を書く。
8. **Cross-cutting Concerns**：セキュリティ・プライバシー、コスト（初回集約と2回目以降の差分など）、運用などのうち、この設計に関係するものだけを書く。
9. **Open Questions**：未決の判断・未確認の事実と、誰に何を確かめれば決まるかを書く。自分のアカウントで既に読めるテーブルに対する根拠のない「他部署への利用ルール確認」などは入れない。なければ「なし」。

## 手順（手戻り防止の必須プロセス）

1. **材料と制約を集める**：依頼、既存のコード・設定・データ・分析レポート、`tk` の記録、連携先リポジトリ（dbt 等）の層ルールや既存テーブルを確認する。
2. **Grill-me で枠組みと主要判断を先に合意する**：
   - 書き始める前に、文書の単位（1本の Design Doc にまとめるか等）、誰がどうなるためのアプリか、抽象度（モデル等はハイレベル方針に留めるか等）、主要な設計判断を `AskUserQuestion` / `ask_user_question` で質問して詰める。
   - 質問文や選択肢には、未定義の内部略称（`課題F`、`d001`、`37上` 等）を使わず、その場で意味が伝わる言葉で書く。
3. **Hunk レビュー用の git 準備**：新しいディレクトリで Design Doc を書く場合は、`hunk diff` / `hunk show` でレビューできるよう `git init` を済ませておく（`push` はしない）。
4. **書く**：上の構成で書く。確認した事実、仮定、提案、未確認を区別し、確かめていない仕様・数値・名前を作らない。仮定は、その仮定に依存する記述の箇所に書く。仮定だけを集めた表や節を作らない。
5. **全文を頭から読み直して自己点検する（提示前に必須）**：
   - ファイルを書き出したら、完了報告の前に必ずファイル全文を頭から読み直し、`explain-before-shorten` スキルを適用して次を点検・修正する：
     - **主語・述語の明示**：すべての文（特に Goals や箇条書き）に「誰が・何に対して・何をする（どうなる）か」の主語と述語があるか。「使う人」「ユーザー」等の相対呼称を使わず、具体的な役割名・モジュール名で書いているか。
     - **用語と数値の一貫性**：元の分析の指標（売上・粗利・客数の区別）や用語（DPT と部門、最適化と計算など）に揺れがないか。独自の言い換え（「物差し」「塊」「失うもの」「解決の道筋」等）が残っていないか。節と節の間で前後矛盾（自動再実行の有無、読むデータ形式など）がないか。
     - **不要な追加の排除**：頼まれていない機能や将来のエンハンス項目が紛れ込んでいないか。
6. **独立レビューの統合（レビュー依頼時）**：複数のサブエージェント（`fable` / `opus`）や `pi` 経由の別モデル（`argon` 等）にレビューさせる場合は、自分の懸念を先入観として渡さずに独立レビューさせ、**両方が挙げた共通の指摘**と**片方だけの指摘**に分けて報告する。

## 確認項目

- タイトルの直後が Context and Scope で、文書そのものの説明や仮定の一覧・表が節の前にも独立した節としても無い
- 必須の9節がこの順にあり、The Actual Design が「解決の方法」から始まり、System-context diagram と Code design がある
- Code design に、作るディレクトリとファイルをすべて載せたツリーがあり、各行に責務が1行で書かれている
- Context and Scope が「目的 → 現状の課題 → 解決策の範囲」の順になっており、既存のコード・データ基盤・インフラの調査結果は Analysis にあり、設計が連携先（dbt 等）の制約に違反していない
- Goals のすべての項目が「誰が・何を見て・何を判断/操作でき・どういう状態になり・どんな価値を得るか」で書かれ、技術的な制約や設計原則が混ざっておらず、Non-goals に頼まれていないエンハンスが混ざっていない
- 機械学習・データ分析の設計書では、The Actual Design が「解決の方法 → システム → データ → 評価」の順で、解決の方法に手法の妥当性・前提・限界が書かれている
- Deployment and Release に、デプロイの方法・ブランチ戦略とリリース戦略（CI/CD）・開発時の検証・インフラの管理方法の4点が、内容または「該当なし」と理由で書かれ、ブランチごとの表（ブランチ名・役割・PR 作成時の動作・マージ時の動作）がある
- Code design で、`infra/` が接続先ごとのモジュールだけで、業務の操作ごとのファイルや業務上の判断を持たず、コマンドラインの入口が `cli.py` に統一されている
- テストと検証の内容が Tests にまとまっており、Alternatives Considered が解決の方法の代替案を比べている
- 「失うもの」「使う人」「ユーザー」「物差し」「塊」「解決の道筋」などの禁止・不自然表現がなく、トレードオフが自然な日本語で書かれている
- Code design で代表的な変更シナリオ（5〜7個）に対する変更箇所の局所性が検証されており、密結合（8モジュール依存等）になっていない
- 書き出した後の全文読み直しを済ませ、指標（売上/粗利/客数）や用語（DPT/部門等）の揺れ・前後矛盾がないことを確認した
