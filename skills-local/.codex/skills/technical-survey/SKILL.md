# 手法ファーストの技術・学術サーベイ（technical-survey）

最適化・機械学習・データ分析・アルゴリズム等の分野について「デファクトの手法」「研究の主流」「現代のアプローチ」「論文ベースの事例」を調査・整理するときは、事例の有無から逆算した曖昧な概説にせず、**「問題の定式化 → 主流の解法 → 並行・発展手法 → 論文で確認できる事例」**の順序（手法ファースト）で構成する。

## 1. 調査手段と裏取りの原則

1. **検索ツールの使い分け**:
   - **Pi**: `web_search` と `web_fetch`、または並列 `subagent`（`google-vertex/gemini-3.8-flash:low` / `gemini-4-hydrogen`）を使う。
   - **Claude Code**: Vertex AI の組織ポリシーで組み込み `WebSearch` が使えないため、自身の `WebSearch` は呼ばず、Bash から `pi -p --no-session --model google-vertex/gemini-4-hydrogen -t web_search,web_fetch "<調査依頼>" < /dev/null`（広範な一次候補収集は `gemini-3.8-flash:low`）を実行して検索・本文読解を行う。あわせて書誌 API（OpenAlex / Crossref / Semantic Scholar / arXiv）の直接取得で DOI・実在・抄録を裏取りする。
2. **「公開事例の少なさ」と「研究・手法の有無」を混同しない**:
   - 企業が競争上の理由で社内運用を公開していないことと、学術研究が存在しないことは別問題である。公開導入記事が少ないことを理由に「自動化されていない」「研究がない」と結論づけてはならない。
   - 企業の適用事例は、原則として**査読論文・国際会議論文・企業の技術論文（テクニカルレポート）として検証可能なもの**に絞って扱う（ベンダーの宣伝記事しかない場合はその旨を明確に切り分ける）。
3. **確認範囲の明示**:
   - 文献ごとに「本文（定式化・実験節）まで確認済み」か「抄録・書誌メタデータのみ確認」かを区別して記録し、読んでいない本文の数式や実験条件を推測で補わない。

## 2. 文書・HTMLレポートの標準構成（手法ファースト）

調査結果は、日本語の明快さを保つため `explain-before-shorten` に従いつつ、次の4章を基本骨格として構成する。Markdown と図解 HTML の両方を作る場合は、章立てと見出し対応を一致させる。

### 第1章：問題の定式化とスコープ境界
- その分野が何を解く問題かを最初に定義する。
  - **入力（与件）**: 何が既に与えられているか（例：店舗の什器配置と通路、各カテゴリーの必要本数など）
  - **決定変数**: 何を決める問題か
  - **制約条件**: 満たすべき物理的・業務的制約（連続性、隣接・分離、容量上限など）
  - **目的関数**: 何を最大化・最小化するか
- 隣接する別問題（例：部門・カテゴリー配置問題と、棚1本の中のSKU棚割問題）との境界を明記する。

### 第2章：研究分野の主流（デファクト）の解き方
- 「この分野では標準的にどう解くか」を結論から1文で言い切ったうえで、処理の段階（①区画化 → ②価値・パラメータ推定 → ③定式化・最適化 → ④後処理など）に分けて具体的に説明する。
- 代表的な系譜（基礎を作った論文と、それを拡張した近年の標準論文）を対応付ける。

### 第3章：並行・発展している別アプローチと使い分け
- 主流手法のどの前提（計算量、需要の独立性、什器固定、データ要件など）が厳しいときに別の手法を使うのかを軸にして、並行するアプローチ（例：メタヒューリスティクス、2段階最適化、シミュレーション連動、強化学習・サロゲートモデル等）を整理する。
- 手法ごとの比較表を置く場合は「前提条件・強み・限界（計算規模や必要データ）・代表文献」を対応付ける。

### 第4章：論文で確認できる実店舗・企業適用事例
- 論文内で実データ検証や実店舗テストが報告されている事例を取り上げ、「対象業態・規模」「使った手法」「比較対象（ベースライン）と報告された効果」「論文外の社内定常運用まで確認できるか」を事実ベースで記述する。
- 検索範囲で見えていない領域（非公開の社内運用、未購読書籍・本文未取得論文など）は末尾に短く切り分けて明記する。
